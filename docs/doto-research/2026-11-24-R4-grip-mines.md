# R4 - grip cancels power aim (P1), Hook Mine lethal switch (P2), mine throw attaches (P3)

Read-only research. Repo `~/github/dishonored2-vr-doto` @ 7ef5612 (nothing edited). Static RE with capstone/pefile on both exes
(scratch helpers in this folder: `disx.py` disasm, `rtti.py`/`bases.py`/`vt.py` RTTI+vtables, `pw.py` power-class slot table, `calls.py`/`sref.py` xrefs).
RVAs are image-relative (+0x140000000). PROVEN = read in code/disassembly. UNVERIFIED = needs a sim/headset read.

## 0. Facts used by all three

**Flat gamepad bindings** (`base/default_keybinds.cfg`, identical D2 and DOTO except `bindingVersion` 44 -> 45):
LT=POWER_WEAPON, RT=MELEE, LB=POWERWHEEL, RB=BLOCK, X=INTERACT, Y=LEAN, A=JUMP, B=CROUCH, L3=SPRINT, R3=ZOOM, dpad=QUICK_0..3.
The ACTION_ name table is the same in both exes (69 names, no new DOTO action). So DOTO's new weapon-mode switch is data-driven (decl) on an EXISTING action.

**Power state flow (D2, PROVEN from disassembly):**
* LT press -> `arkPlayerStateUsePower` (state 63, vtable `0x1c80ed8`). Its enter (`0x856160`) calls the equipped power's StartAim virtual (`call [power_vt+0x118]`, `0x8561f9`).
* LT release -> state slot `0x1c80f90` = `0x8566f0` (the release handler): `power = list(state+0x58, 2)`; if `0x61bce0(power,0)==0` and `power+0xa4` (aim active) != 0 it calls the power's **Cast** (`call [vt+0x120]`, `0x85674d`); then ends the state (`0x8551c0`).
* State exit (`0x8564e0`, slot 0x60): `if(power+0xa4) call [vt+0x128]` = **StopAim**, no Cast.
* So "release LT while aiming" == cast. "Cancel" == leave the state/StopAim before the release handler runs.
* Slots per class (`pw.py`, vt+0x118/0x120/0x128 = StartAim/Cast/StopAim): Blink `0x61dc90/0x61ec20/0x61e980`; **Far Reach = `arkCpntPowerGrapple`** vtable `0x1b52818` `0x43f300/0x43f7c0/0x43f620`; Doppelganger `0x43ddc0/0x43c950/0x43c860`; Possession `0x447ba0/0x447db0/0x447cf0`; Domino=`arkCpntPowerPhantasmalLink` `0x446fe0/0x447170/0x447160`; Mesmerize, DevouringSwarm, Windblast, DarkVision, ShadowWalk, Bendtime each have their own.
* `m_cancelActivePowers` (bool) exists in the player-state decl base (typeinfo ctors `0x174f98b`, `0x17d9a83`; decl-name table `0x1381c10`): a state that sets it cancels active powers on entry. WHICH states set it is in the .decl data, not in the exe. UNVERIFIED.

## P1 - Far Reach (and every hold-to-aim power): the grip casts

### Input -> action path (all in `src/dxgi_probe.cpp` unless noted)
1. Left trigger value reaches the pad: `compose()` `src/controller_input.hpp:137-141` (`power_trigger()` :56-67 holds a clean 0/1 hold with a 2-frame/30 ms release debounce; `left_trigger_instant` :139 bypasses it for gadgets).
2. Left **grip is NOT LB in gameplay**: dxgi_probe.cpp:16999 `input.left_grip=0 // Grips belong to the hands; LB comes only from the wheel`. (Wheel: :17320 sets `left_grip=1` only while the wheel is open; `controller_input.hpp:119-129` turns it into LB.) So the grip does not send any native "cancel".
3. What the grip does instead (left hand, a power in slot 1):
   * `GripIntent` (`src/vr_controls.hpp:418`): grip first then trigger = `fist` -> `pass_trigger=false` -> LT zeroed (:17151). Trigger first (>=100 ms) then grip stays `Kind::trigger`, `pass_trigger` true (no effect).
   * `GripTriggerGuard` (`src/play_controls.hpp:101`) only swallows a trigger pressed AFTER the grip (:17805 `if(grab_guard[rh] ...) input.left_trigger=0`).
   * **Root cause, dxgi_probe.cpp:17682**: `input.right_trigger=0; if(raw_grip(rh)>.55f && !gun_grip.held() && !left_gadget && !timepiece_out() && !left_forearm_gun.load()) input.left_trigger=0;` ("a fist never fires"). Inside `if(logic==2)` (:17650), unconditional in gameplay. With a power equipped and LT held, squeezing the grip (>0.55) writes LT=0, which `compose()` passes to the game 2 frames / 30 ms later as a plain LT release -> the UsePower release handler `0x8566f0` -> Cast. That is exactly "Grip instead executes the Far Reach". PROVEN by reading; the headset effect matches the issue text, not simulated.
   * Secondary (:17467) `interaction.consume_trigger -> left_trigger=0` has the same effect if a grip Use claims the target Far Reach is pointed at (grip "use" -> native X, :17749-17751).
4. The hand-aimed Blink (`src/native_blink_aim.hpp`, hook `0x1406205e0` per-frame job; writes only the camera aim axis `cam+0x25288`, :150-170) only steers the ray; it has no cancel logic and does not read the grip. There is NO hook on Far Reach (Grapple) at all: its aim uses the camera aim written by the generic left-aim route.

### How the flat game cancels - UNVERIFIED
No dedicated cancel action exists (names above). Candidates: Block (RB/Ctrl), Melee (RT/LMB), Jump/Crouch/Use presses entering a state with `m_cancelActivePowers`. This needs a one-time measurement (scenario S1b below). Do not guess the mapping in code before it.

### Fix plan
Stop the accidental cast first (certain), then add a real cancel.
1. **dxgi_probe.cpp:17682** - exempt a held power aim: add `&& !power_aim_held` where `power_aim_held = left_power && raw_trigger(rh)>=.55f && trigger-first` (the left hand holds a power item; `left_power`/`left_power_item` already exist, :5906/:5931). Also exempt in :17151 (`pass_trigger`) and :17805 (grab_guard) for a trigger that is already an aim (they only bite trigger-after-grip, but keep one rule). While a power aim is held, the hand's grip must NOT start Use/grab (route `grip_use[h]`/`native_grab` off for that hand) so the grip is free to be the cancel.
2. **Cancel = grip squeeze while aiming** (new small header `src/native_power_cancel.hpp`, same install/verify style as `native_blink_aim.hpp`):
   * Preferred (engine-exact, no guessing which button): MinHook the UsePower release handler `0x8566f0` (D2; vtable slot `0x1c80f90`; DOTO needs the port.py map entry, UsePower id 63 is unchanged in DOTO per `tools/doto/reviews/powers-re.md` row 23). Wrapper: `if(cancel_latch && power=list(state+0x58,2) && power[+0xa4]) call [vt+0x128] (StopAim)`, then call the original. The original then sees `+0xa4==0` and skips Cast (`0x85673f cmp [rbx+0xa4],al / je 0x856765` -> straight to state end). The latch is set by the Present thread when grip rises >=.55 while a power aim is held, cleared when LT is released. Class-independent (Blink, Far Reach, Domino, Doppelganger, Mesmerize, Windblast, Possession, DOTO Displace): all inherit StopAim at vt+0x128. Gate: only when `0x61bce0`-ready and `+0xa4!=0`; SEH-guard; prologue pin like blink_aim.
   * Fallback (no new hook): once the cancel button is measured (S1b), pulse that native button (as `input.b` crouch pulses do, e.g. :17463) for one frame and keep LT held until the player lets go; then release LT only after the state left (read state 63 via `native_player_state`).
3. Haptic pulse on cancel (`game_xr->pulse`) and a status counter.
4. Do not remove the "fist never fires" rule for non-power hands (gun/sword); restrict the exemption to `left_power`.

### Other hold-to-aim items
* Same path, same bug: every power on LT (Blink for Corvo and Emily, Domino, Doppelganger, Mesmerize, Windblast, Possession, Devouring Swarm), DOTO Displace (`arkCpntPowerSwapper`: its cancel is state DespawnSwapper 101, `powers-re.md:81`; the generic StopAim at exit still applies). Bend Time (`arkCpntPowerBendtime`), Dark Vision, Shadow Walk are toggle/hold effects, not aims: a grip zeroing LT ends Shadow Walk (hold) - same exemption helps.
* Gadgets are NOT affected: `left_gadget` branch (:17815-17832) already owns LT (`left_trigger_instant`); the grip IS the hold there (grenade: opening the hand releases/throws; mine: tap). Their "cancel" is the open hand = drop (:17823) in dual wield, and in non-dual-wield opening the fist releases LT = place/throw (:17828). So for gadgets "grip = hold, not cancel", by design; there is no cancel gesture for a grenade pin/mine ghost either (UNVERIFIED desire).
* Sword Void Strike (DOTO) / power strike (D2) use grip+trigger by design (`sword_charge.hpp`), unrelated.

## P2 - DOTO Hook Mine lethal / non-lethal switch

### What the mod does today
Nothing. There is no code anywhere for gadget/mine mode, ammo switch, or weapon states (grep `ammo|alternate|lethal|WeaponStates` in `src/`: only the crossbow/pistol bolt code `native_ranged_fire.hpp` - `0x63a490` "the game's own ammo switch", wheel picks - which has no Hook Mine path; `tools/doto/reviews/weapons.json:2499` says HookMine components are "not re-checked"). Hook Mine support = (a) the DOTO placement sensor hook (`native_gadget_aim.hpp`, DOTO sensor `0x400990`), (b) `native_gadget_drop.hpp` kind table (`Kind::hook_mine`, pickup `ammo_hook_mine.def`), (c) the shared gadget grip/tap logic `src/throw_gesture.hpp:48 GadgetGrip`, dxgi_probe.cpp:17815-17832. The grip is spent on holding the mine; it is not LB either (:16999), so no native action is sent.

### Engine facts (DOTO exe, PROVEN unless marked)
* Classes: `arkCpntHookMineEquipment` : `arkCpntWeaponPlaceableAfar` : `arkCpntWeaponPlaceable` : `arkCpntWeaponRanged` (vtables `0x1c43928/0x1c43ac8`); thrown projectile `arkCpntHookMineThrowable` : `arkCpntRigidBodyThrowable` (`0x1c43cb8`); behaviour component `arkCpntHookMine` (`0x1c43548`) with FSM `THROWN, STUCK_PENDING, STUCK_READY, GRAB_ACQUIRING, DRAGGING, TEARING_OFF` (+ `DRAG_*`). (`bases.py` output.)
* Lethality is NOT an ammo item. String: "Weapon state component is needed in order to know if hook mine is lethal or not." = `arkCpntWeaponStates` (vtable `0x1c45e18`, decl `stateDesc` + `stateTransition` lists, `stateIndex_t`), which the equipment reads (equipment vslot `0x3b1b40/0x3b1b60` return the states-owner object `+0x778` and its field `+0xc`). The Voltaic Gun also uses WeaponStates (`weapons.json` blockers).
* Switching is a PLAYER STATE: `arkPlayerStateChangeWeaponState`, id **0x49 = 73** (enum table `PLAYER_STATE_CHANGE_WEAPON_STATE`, lea at `0x1b12943`, decl ctor `0x151e04c` stores 0x58 size; vtable `0x1cbbf78`). Slot `0x30` (`0x6da060`): requires an equipped weapon (via `0x869e90(owner,1,..)`) whose vslot `+0x110` says it can change state; update `0x6da320` runs a timer (decl +0x90 duration) and clears an input-claim bit in the controller (`[machine+0x350]+0x98`); exit `0x6d9fc0` posts message `0x1ed` with the weapon's id. This is the DOTO analogue of the bolt swap.
* Input: no new ACTION in the exe and the shipped `default_keybinds.cfg` binds nothing extra, so some existing action (the decl routes it) enters state 73. UNVERIFIED which one. Plausible: ZOOM (R3), an LB tap, or an equip/quick-slot re-press. Do not hardcode.
* Hook mine is two-valued: `arkMsgHookMineForceStun` / `ARK_MDNT_MSG_HOOK_MINE_FORCE_STUN`, HUD `arkUILethalStatus_t`, attribute `ARK_ATTRIBUTE_HOOK_MINE_SIZE_FACTOR`. The pulled-in enemy `m_draggedLethally`.

### Why the VR grip does not switch it
The grip never reaches the game as any action in gameplay (:16999) and in dual-wield it is the "hold the gadget" squeeze (GadgetGrip `held`). Not the P1 bug (P1 zeroes LT; here nothing is sent at all), but the same root pattern: the grip's native button output is swallowed because grips belong to the hands.

### Fix plan
1. **Find the native trigger (cheap, no game change)**: sim scenario S2 (below) pulses, one at a time with Hook Mine equipped, native X, Y, B, A, R3, RB, a 120 ms LB tap and the dpad, and records after each whether player state 73 turned active (existing helper `d2vr::native_player_state(reader,image_base,machine,73,0)` as used in dxgi_probe.cpp:17795) and the weapon-states index changed.
2. **Mod gesture**: a dedicated switch gesture that does not compete with hold/cast: e.g. a SECOND grip squeeze of the OTHER hand while the mine hand holds it, or a long squeeze (>=600 ms) of the holding hand while the trigger is up, with a haptic + HUD cue. (The user's "grip" request fits the long/second squeeze; a plain squeeze already means hold/drop.) Implement next to `GadgetGrip` (`throw_gesture.hpp`) as a pure `GadgetModeSwitch` class (testable like `tests/gadget_aim_check.cpp`), output `mode_switch` pulse.
3. **Delivery**: preferred = pulse the measured native button for one frame (route through `PadComposer`, like a face-button pulse). Engine-direct fallback = the DOTO state-request routine used by the mod's takedown/equip helpers (`0x869760(machine, 0x49, request)`, D2 twin: same shape, `powers-re.md` notes `0x869760`; needs `port.py` rule + a new `offsets.json` entry), gated on `ChangeWeaponState` can-enter (slot 0x30 / equipment vslot `+0x110` true).
4. D2 has no equivalent (stun mine / spring razor have no modes): trait-gate with a new `game_traits::gadget_mode_switch` (true in DOTO only), like `grenade_spawn_follows_velocity`.
5. Open design check: the mine hand's own physical grab of another object must not be confused with the switch squeeze (guard with `native_grab.holding`).

## P3 - a thrown mine should attach like the flat game

### What the mod does to a mine "throw"
Three distinct routes (all PROVEN by reading):
1. **Grenade hand throw** (`src/native_grenade_throw.hpp`, hook `0x87c2a0`, return `0x633341`): rewrites velocity AND spawn of `arkCpntWeaponThrowable::Throw` for `arkCpntGrenade` only (:57 `is_grenade`; docs `native-throw-hand-velocity.md` "Mines and spring razors are not thrown by hand"). Off in DOTO (`game_profile.hpp:31 grenade_spawn_follows_velocity=false`; DOTO Throw frame has the launch point 0x10 BEFORE the velocity). Mines never go through it: both games' mine equipment is `arkCpntWeaponPlaceable` (D2 vtable `0x1b54538`, DOTO HookMineEquipment inherits `PlaceableAfar : Placeable`), not `WeaponThrowable` (D2 vtable `0x1b9d8b8`).
2. **Native placement/throw, hand aimed** (default non-dual-wield path, and the trigger TAP in dual wield `GadgetGrip` :48-70, `tap_until_`=150 ms): the engine's own placement runs; the mod only moves its ray start/direction to the left hand (`native_gadget_aim.hpp`, doc `native-gadget-hand-aim.md`: Placement `0x3C1E40` D2, ThrowHit `0x3CEC30`; DOTO Placement `0x400990`). The engine then spawns the placed/thrown entity itself; for the Hook Mine that is `arkCpntHookMineThrowable` entering `THROWN -> STUCK_PENDING -> STUCK_READY` (engine attach). Nothing in the mod replaces that projectile. If it does not stick the cause is in the INPUT to the engine: UNVERIFIED candidates (see below).
3. **Grip opened with a mine in hand = "toss"** (dual wield, dxgi_probe.cpp:17823 -> `NativeGadgetDrop::drop`, `native_gadget_drop.hpp`): spawns the mine's **world pickup def** (`ammo_hook_mine.def` / `ammo_stun_mine.def` / `ammo_springrazor.def`, kind table :50-56) and flies it with the mod's own physics (`GadgetFlight` :88-, sphere casts, gravity 9.81, <=3 bounces, `engine_teleport` every frame), resting "flat on the surface it met". No engine attach logic ever runs: the entity is a loot pickup whose embedded mine component (D2 comment :18-19, "whether it can strike while lying is unverified") sits in `INACTIVE`/lying state; DOTO's HookMine component is not even probed (`read_probe` :480-486 only types D2 `mine_vtable`/`stun_mine_vtable`). So a hand-thrown mine in dual wield is a prop, never `STUCK`. **This is the proven reason a thrown mine does not attach**; it is by design of v768 ("toss and catch every held item").

### UNVERIFIED sub-causes of route 2 (check in sim before changing)
* The throw-preview sensor ThrowHit takes its direction from `[player+0x30C]` x,y with **z forced 0** (`native-gadget-hand-aim.md` "ThrowHit"): its hit prediction is horizontal, so a pitched hand throw may find no surface and the engine drops at the feet.
* DOTO's Hook Mine uses `PlaceableAfar`; whether it samples the same Placement sensor (`0x400990`) or a different sensor (Displace's afar marker uses BlinkSwapper/Cross sensors) is not shown. If different, the hand aim does not reach it (marker/ghost stays on the head ray). Check `gadget_aim.placement[1]` (swapped) rises while a hook mine is aimed.
* Spawn inside hand collision: not evidenced; the engine launches from the weapon's own muzzle/launch frame, not the drawn hand.

### Fix plan (keep hand aim, let the engine attach)
Replace the mine "toss" with an engine placement fired along the throw:
1. In `GadgetGrip::update` (`throw_gesture.hpp:55-70`) for `!grenade`: when the grip opens unarmed (`o.drop`) AND the hand speed over the last 100 ms (existing `ThrowGesture` ring: `note_hand`) exceeds ~1.5 m/s, do not drop; instead emit `throw_place` = a native trigger tap (150 ms, same `tap_until_`) and publish a **throw aim** to `NativeGadgetAim`: placement ray origin = the hand, direction = normalised hand velocity (pitch limited like `blink_aim_axis_from_hand`, +-85 deg), valid for ~250 ms. Extend `gadget_aim_wanted` (`src/gadget_aim.hpp`) with the throw-aim override and, for ThrowHit, drop the z=0 forcing (swap field `[s+0x10]+0x30C` z) so the prediction follows the real arc. The engine then raycasts, validates the surface, spawns its own placed mine / `HookMineThrowable` and runs its attach (`STUCK_*`, `deferredSticking_t`, `ARK_MSG_THROWABLE_STUCK`).
2. If the placement is refused (no surface within range, ghost invalid), fall back to the current `NativeGadgetDrop::drop` toss (unchanged behaviour). Keep `build/no-hand-mine-aim`.
3. D2 vs DOTO: D2 stun mine / spring razor: Placement `0x3C1E40` + ThrowHit `0x3CEC30` pins exist and are verified (docs). DOTO: Placement `0x400990` mapped (`weapons.json` notes), ThrowHit twin and the Afar sensor need confirming through `tools/doto/fn_diff.py 0x3CEC30` and a read of which sensor `0x3c2e50..0x3c3070` (PlaceableAfar vslots) consume. Grenades stay on `native_grenade_throw` (DOTO still off until the frame is confirmed; separate item).
4. Do NOT spawn `arkCpntHookMineThrowable` by hand: the throwable def name and its init messages are unknown, and runtime spawns have never simulated their physics components (v407/v413 note, `native_gadget_drop.hpp:12-14`).
5. Never route a toss through `NativeGrenadeThrow`: its `is_grenade` check rejects mines (counts `not_grenade`).

# R5 - Possession: controls not aligned with camera (D2 VR mod)

Read-only. Repo: ~/github/dishonored2-vr-doto, D2 exe static RE (RVAs). PROVEN = read in code/exe. UNVERIFIED = needs a live read-only /proc/mem sample.

## 1. Normal play: how stick movement follows the view (PROVEN)
Head yaw is folded into the PLAYER heading by "head-follow", and the stick is rotated by the not-yet-absorbed remainder.
- src/head_locomotion.hpp `HeadFollowing`: `publish()` stores the head yaw (`tracked_yaw`, room-relative, dxgi_probe.cpp:10315-10317, only `per_frame && game_logic_mask()==2`, `usable` = XR focused && `!body->authored_view()`). `delta()` (l.~44) = clamp(head_yaw - compensation, +-6 rad/s*dt), 0 unless native_ready && fresh(250 ms). `commit()` accumulates `compensation_`. `relative_yaw(now)` = head_yaw - compensation, NaN when stale/unusable.
- src/native_turning.hpp `invoke()` (hook on physics step RVA 0x1b4760, `step_rva`): when `ready()` (l.~46: `!authored_view()`, look[1]~0, no physics yaw velocity/impulse) and `logic_()==2`, it sums stick turn (`control_.consume`) + head-follow `physical_delta` and calls `add_yaw_` = RVA 0x1b2ff0 on the PLAYER'S heading delegate (`before->heading_delegate`, +0xd0 = heading; l.~110-117), only if `heading_delegate == delegate` of the step being hooked, then verifies `[delegate+0xd0]` == expected.
- Stick: `NativeTurning::orient_movement()` (native_turning.hpp:161-165), called from dxgi_probe.cpp:17984, does `head_directed_stick(move_x,move_y, head_follow_.relative_yaw(now))` (head_locomotion.hpp:~20, a plain 2D rotation; NaN -> pass-through unrotated, comment: "the native camera already follows the head"). Right-stick turn: `NativeTurning::publish()` (l.~188) zeroes `input.turn_x` when it claims the turn (dxgi_probe.cpp:17983).
- So: view yaw = player heading + (head - compensation) in room frame; movement frame = player heading; stick rotated by (head - compensation) => forward = where the head looks. Any pass-through of the stick relies on the game's own frame = player heading.
- `authored_view()` (native_player_camera.hpp:95) = camera mode!=0 || target_mode!=0 || blend_body_yaw || code_lock (except tracked shadow walk mode 7). Camera fields: mode +0x25200, target +0x25204. It also gates `ready()` and `usable` above.

## 3. What the mod does during possession today (PROVEN: nothing possession-specific)
`grep -i possess src/` finds only comments (power_cancel.hpp, native_melee.hpp). No state-26 / controller-state / host-entity read exists. Therefore:
Case A (camera mode stays 12/!=0, i.e. authored_view() true): `ready()` false and `usable` false => no head-follow, no stick turn applied, `publish_head(...usable=false)` => `relative_yaw` NaN => stick passes through UNROTATED (head_directed_stick returns early). Tracked head still renders on top of the (authored) host camera through the authored-camera anchor path (dxgi_probe.cpp:10089, `AuthoredCameraAnchor`). Result: view yaw = host camera yaw + head offset (user looks 60 deg right); movement frame = host body yaw => stick-forward goes where the host faces, not where the user looks. Right-stick turn: `publish()` claims and zeroes turn_x but nothing is applied (not ready) => turn input is swallowed (host cannot be turned by stick either).
Case B (camera mode 0 again, camera follows host): `ready()` is true as long as `look[1]`~0 and the player's physics step runs; `invoke()` then writes yaw to the PLAYER's heading delegate (the parked body, 0x1b2ff0), NOT the host; compensation grows, `relative_yaw` ~0, so the stick is NOT rotated although the host never received the turn; view yaw = host frame + head offset; movement = host frame. Same mismatch (plus `feedback_.poll` may mismatch `s.heading` vs entity_heading and soft-fail/cancel, native_turning.hpp `fail()`; >20 soft fails in 10 s latches `failed_`, which would disable turning for the rest of the session).
Either way: mismatch = (head yaw offset relative to host forward) which the mod never compensates. It is exactly the report ("controls not aligned with camera direction").

## 4. Fix options
(a) Rotate the stick by (view yaw - host movement yaw) while possessing. Hook: `NativeTurning::orient_movement()` (native_turning.hpp:161) / its call (dxgi_probe.cpp:17984); needs the view yaw = yaw of the rendered per-eye centre (already computed at dxgi_probe.cpp:10147-10317, `centre_pose` + `head_origin` + anchor basis) and the host frame yaw. Independent of which entity the game turns; no engine writes; small blast radius. Risk: need the host's real movement frame (UNVERIFIED which vector the engine uses: host reference frame row 0 [`arkCpntReferenceFrame`] vs the camera yaw `cam+0x25274`), host rotating under the stick (re-evaluate every frame, which this does).
(b) Drive the host yaw (AddYaw on the host's heading delegate). Risky: the host is an AI body with its own heading owner, different class per host (human/rat/fish/corpse/swarm), verified-write pattern in native_turning relies on the player's physics object layout (+0xd0, +0x160/0x168/0x1e0 checks).
(c) Recenter head to host at possession start + snap turn on host: needs (b) anyway, plus a recenter hook.
RECOMMEND (a), and while possessing (1) do not claim the right-stick turn (`publish()`: pass `gameplay=false` or skip), so the game's own look turns the host and view follows; (2) freeze head-follow (`usable=false`, `delta()` 0, no `add_yaw_`) so the PLAYER body is never turned in Case B; (3) rotate the left stick by (head yaw relative to the host forward at render time). Keep normal-play path untouched: gate everything by `possessing`, `orient_movement()` default branch unchanged (locomotion accepted by the user).
Detection (D2): add to `native_action_camera_states` or a sibling reader the player FSM state 26 {index 0x1a, vtable 0x1c79878} using the existing receipt pattern (native_action_camera.hpp:69-100 reads `[[machine+0x90]+0x10+idx*8]`, `+0x20` active byte, `+8` index, `+0x10` machine). UNVERIFIED whether state 26 stays active for the whole possession (it is "Enter" - could end after the fly-in): fallback signals = camera mode/target 12 (native_player_camera.hpp, `mode`/`target_mode`), `arkCpntNPCPossession` present on a nearby host with active flag, or hooking ARK_MSG_POSSESSION_BEGIN/END (arkMsgPossessionBegin/End). Do a live read-only sample first: during possession log camera mode/target, FSM active bytes for ids 26/63/0, player `+0x300` pos vs. the camera pos (`s.view`), and the host entity's position.
DOTO: no possession power (feature-parity.md l.211: Semblance "not implemented"). DOTO exe still carries `arkPlayerStateEnterPossessedHost` (camera mode 0xc, powers-re.md l.271; decl push 0x89c555 in DOTO exe, id differs from D2's 0x1a - re-derive via the decl ctor `[decl+0x60]`), so a D2-only fix is enough; keep the detector table per-build (tools/doto translation layer).

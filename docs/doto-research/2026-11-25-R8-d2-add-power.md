# R8: giving the player a power in Dishonored 2 (AddPower / AddPowerUpgrade)

Static RE only (capstone + xref scan). Binary: Dishonored2.exe, Steam build 17576867, image base 0x140000000; every address is an RVA.
Goal: a test command `d2vr give power possession|far_reach` so the Corvo/Blink-only lab save can exercise the Possession code.
Tags: **PROVEN** = seen in the disassembly; **INFERRED** = follows from the code but not observed at runtime; **UNVERIFIED** = guess.

## TL;DR

- `arkCpntPlayerPowerSystem::AddPower` = **0x455850**, `bool __fastcall AddPower(arkCpntPlayerPowerSystem* ps, int arkPlayerPower_t)`. The argument is a plain enum: **Possession = 7, Far Reach (`GRAPPLE`) = 6**, Blink = 2. You don't need a decl lookup or a name. PROVEN
- `ps` is the player entity's `arkCpntPlayerPowerSystem` component (vtable **0x1b550e8**). You can find it by walking `player+0x268` for that vtable, or with the engine's FindComponent `0x877720(player, base+0x39e2bb0, 0)`. PROVEN
- AddPower is the standard inventory pickup: `arkCpntInventory::AddItem(inv, powerItemDecl, 1)` (0x6156e0). It spawns the power's equipment entity and component and posts the item-added events. It then removes the power's **rune cost** from the inventory, clamped at 0. It does **not** check that you can afford it. It does **not** equip. PROVEN
- If you don't want runes taken: call `GetPowerItem 0x456b70(ps, 7)`, then `AddItem 0x6156e0(inv, decl, 1)` yourself. INFERRED equivalent (it is the first half of AddPower).
- Game thread only (it allocates and spawns an entity). PROVEN that it allocates and spawns. The game-thread requirement is INFERRED.

### AddPower 0x455850, step by step (PROVEN)

1. `inv = CheckedGet(ps+0x20, 2)`: the power system's checked pointer to the **player's arkCpntInventory**. It is set at attach (0x457710), from `FindComponent(GetPlayer(game), &arkCpntInventory_typeinfo 0x39dcd30, 0)`. GetPlayer 0x8a8ba0 = `*(game+0x3130b0)`, and `game = *(base+0x39a5290)`, the same path as `read_powers`.
2. `0x6144e0(inv, 9, &list)` collects **every** inventory record whose `decl+0x60 == 9` (type 9 = power). Count 0 records are included. The count > 0 variant is 0x614550. Records sit at `inv+0x38`, count at `inv+0x40`, stride 0x38; `+0` item decl, `+0x10` equipment component, `+0x20` count, `+0x24` max.
3. For each record it looks up `{itemDecl, equipDecl}` in `ps+0x80` (count `ps+0x88`, stride 0x10) and matches `equipDecl+0x190 == power`. The list is built in 0x4561d0, which the vtable slot at 0x457790 (start) calls. For every type-9 record it takes `itemDecl+0x80` (entity def), runs the decl manager vfunc +0x1c0, then `0x877920(def, arkDeclCpntEquipment typeinfo 0x3987bb0, 1)`. This means equipDecl is the power entity's **arkDeclCpntEquipment**, and `+0x190` is its `arkPlayerPower_t`.
4. `AddItem(inv, itemDecl, 1)`. It must return 1. A power already owned at max returns 0 and fails.
5. On success: `RemoveItem 0x614750(inv, *(ps->decl(+8) + 0x498), *(int*)(itemDecl+0xc8))` = removes `cost` of the rune item. The removal clamps at 0 (0x63c800), and nothing checks affordability. Returns true.
   - That `decl+0x498` is the rune item and `itemDecl+0xc8` is the rune cost is INFERRED (the UI caller passes a "cost" argument, and this is the only other inventory change).
6. On failure it logs "could not add power." through 0x166830 and returns false.

What does `equipDecl+0x190` hold? It is `arkPlayerPower_t`, PROVEN. Code compares the current power's `decl+0x190` with constants:
- 0x68ebc7 `== 0xc` in a vtable of `arkPlayerStateUsePhantasmalLink`. 12 = `ARK_PLAYER_POWER_PHANTASMAL_LINK`.
- 0x692407 `== 0xa` in `arkPlayerStateUseWindblast`. 10 = `WINDBLAST`.
- 0x8393ee `== 2` = BLINK, and 0x687752 `== 6` = GRAPPLE.

The enum reflection table is at 0x2386bb8. Entries are `{"int", name, "value"}` triples:

GRAPPLE is Far Reach. The repo's far_reach vtable 0x1b52818 is RTTI `arkCpntPowerGrapple`, and Possession 0x1b531c8 is `arkCpntPowerPossession` (PROVEN, RTTI).

### AddItem 0x6156e0 for a type-9 record (PROVEN)

Types 1/0xf, 0x10 and 0x1a take special paths. Type 9 goes through `0x614f30` (find the record index by decl; -1 means return 0) and then `0x615840(inv, idx, count)`:

- `0x63c9f0` adds to `+0x20`, clamped to max `+0x24`, and sets the new flag `+0x28` on 0 to n.
- `0x6170b0` posts event 0x1ad. On 0 to n it runs `0x619380`, which **spawns the item's equipment entity** from `itemDecl+0x80`, finds its equipment component, attaches it to the record (0x63cb90) and adds it to `inv+0x58`. It also runs `0x6139f0`, and sets record `+0x34 = 1` when the owner is the player.
- It then posts event 0x9b and sends an owner message `'d'` (0x884920).

So after a successful give, the power's component exists in the inventory record `+0x10`. That is what `read_powers` and `test_equip "power:<vtable>"` look for. INFERRED: count 0 records have a null `+0x10`, which is why the observer shows Blink only today.

Important precondition: AddItem/AddPower can only raise the count of an **existing** record. It never creates one (PROVEN: 0x614f30 returns -1, which leads to return 0). The normal purchase path has no other way to add a power, so the player inventory must already carry a count-0 record for every buyable power. INFERRED, very likely. If `GetPowerItem(ps,7)` returns 0 in the lab save, this assumption is wrong for that save.

### Callers (PROVEN)

- AddPower and AddPowerUpgrade each have a single caller: **0x521580**, `arkJournalSectionPowers` Flash callback **"OnPowerUpgradeAcquired"** (registered at 0x522283; the class vtable 0x1b756a8 holds 0x522270).
  - Arguments come from Flash: `cost`, `isRootUpgrade`, `powerUpgradeID`.
  - `isRootUpgrade ? AddPower(ps, id) : AddPowerUpgrade(ps, id)`, with `ps = CheckedGet(journal+0x58, 2)`.
  - On success it runs `0x18fdc0`, then `0x78d1f0` (UI/game-logic refresh, UNVERIFIED), and writes `cost` back.
  - So the power menu purchase is the only caller. There is no script/Kiscule node and no console command, and no caller takes a name.
- GetPowerItem: one caller, 0x522390, "ShowTutorialPower" (journal). HasPower: one caller, 0x5216e0 (journal).
- AddPowerUpgrade 0x455ab0 loops over 0x26 slots of `ps->decl+0x88` (`{int arkPowerUpgradeId_t; itemDecl*}`, stride 0x10), matched through the enum descriptor at `[0x32cdea8]`. It runs `AddItem(inv, upgradeItemDecl, 1)` and then removes the same rune cost. The upgrade ids come from the table at 0x238a1f0:

| Power | Upgrade ids |
|---|---|
| Far Reach | 19 PULL_OBJECTS, 20 PULL_ENEMIES, 21 PULL_ATTACK, 22 DECELERATE |
| Possession | 23 CHAIN_HOST, 24 EXTENDEDDURATION, 25 PARASITE, 26 DECAYEDHARBOR |

  The upgrade slot table at `ps->decl+0x88` is PROVEN from the decl constructor 0x455000 (0x26 entries at +0x88, 0x19 enhancement entries at +0x2f8, rune decl at +0x498).

## 3. The argument

No decl or name is needed: pass `7` (Possession) or `6` (Far Reach).

To check the item before giving (and to give it without a rune cost), use `GetPowerItem 0x456b70(ps, 7)`. It returns the item decl whether the count is 0 or not. The item's name string is at `itemDecl+0x8`, the same field `test_equip` reads (PROVEN live v769). Log it as evidence.

A name fallback, with no engine call: iterate `inv+0x38` records with `decl+0x60 == 9` and match `*(decl+8)` against "possession". The decl paths are not in the exe strings, so this route is UNVERIFIED.

## 4. Safety and usability

- **Thread: game thread only.** INFERRED. It allocates idLists with the engine allocator (0x1548e0), spawns an entity through the decl manager (0x619380), and posts entity messages and events. Queue it like `Op::test_equip` in NativeWeaponHands' game-thread service (src/native_weapon_hands.hpp:238), wrapped in `CrashOperation` and try/catch.
- Call it once. A second call returns false (count at max), which is harmless.
- **Runes:** AddPower takes `itemDecl+0xc8` runes. This clamps at 0, so a 0-rune save loses nothing. Use the GetPowerItem + AddItem route to keep runes. INFERRED.
- **Not equipped:** follow with the existing `test_equip "power:1b531c8"` (Possession) or `"power:1b52818"` (Far Reach). PROVEN that AddPower has no equip call.
- **Mana:** the cast uses the player's normal mana. Nothing else must be set for the base power. The power-wheel listing should follow from the item-added event 0x9b and `0x6139f0`. UNVERIFIED: check the wheel after the give.
- **Save state:** the inventory count is ordinary saved state. Saving after a give makes it permanent in that save. Don't save the lab save, or keep a copy.
- DOTO: the same functions exist in that engine family, but these RVAs are **D2 only**. Gate the command to D2 (`game_traits`) until DOTO's are ported.

## 5. Call sketch

```cpp
// game thread (NativeWeaponHands service op), D2 only
using AddPowerFn     = bool(__fastcall*)(void* ps, int power);              // 0x455850  PROVEN
using GetPowerItemFn = void*(__fastcall*)(void* ps, int power);             // 0x456b70  PROVEN
using AddItemFn      = int (__fastcall*)(void* inv, void* itemDecl, int n); // 0x6156e0  PROVEN
using FindCpntFn     = void*(__fastcall*)(void* ent, void* typeinfo, int);  // 0x877720  PROVEN
constexpr int kFarReach = 6, kPossession = 7;                               // arkPlayerPower_t PROVEN

bool give_power(uintptr_t base, int power, bool free_of_runes) {
    // byte-check 0x455850 / 0x456b70 / 0x6156e0 / 0x877720 prologues (table above) first
    auto game = *(uintptr_t*)(base + 0x39a5290);                 if (!game) return false;  // PROVEN
    auto player = *(void**)(game + 0x3130b0);                    if (!player) return false; // PROVEN (0x8a8ba0)
    auto ps = ((FindCpntFn)(base + 0x877720))(player, (void*)(base + 0x39e2bb0), 0);       // PROVEN
    if (!ps || *(uintptr_t*)ps != base + 0x1b550e8) return false;                          // vtable PROVEN
    auto item = ((GetPowerItemFn)(base + 0x456b70))(ps, power);  // 0 => no record in this save (INFERRED precondition)
    if (!item) return false;
    if (!free_of_runes) return ((AddPowerFn)(base + 0x455850))(ps, power);                 // the purchase path, takes runes
    // the same as AddPower's first half, no rune cost (INFERRED equivalent)
    struct Checked { int serial; int pad; uintptr_t cpnt; };
    auto c = (Checked*)((uintptr_t)ps + 0x20);                   // CheckedGet(ps+0x20,2) in the game (0x3da910)
    if (c->serial == -1 || !c->cpnt || *(int*)(c->cpnt + 0x18) != c->serial) return false;
    if (*(uintptr_t*)c->cpnt != base + 0x1b9a878) return false;  // arkCpntInventory PROVEN
    return ((AddItemFn)(base + 0x6156e0))((void*)c->cpnt, item, 1) == 1;
}
// then: test_equip("power:1b531c8") to put Possession in hand; check read_powers present[] lists "possession".
```

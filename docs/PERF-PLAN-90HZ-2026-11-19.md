# Performance plan: hold 72 / 90 Hz in the heavy areas (2026-11-19)

Goal: a stable 90 fps on most players' PCs and at least 72 fps in the heavy areas on the user's rig, comparable to Metro Exodus
VR, Dying Light VR and BetterVR (Zelda). This plan is built from the logs already on disk and the reference-mod research of
2026-11-19. Nothing here has been run yet. Estimates are marked as estimates.

**Status (night of 2026-11-19): see `docs/PERF-NIGHT-2026-11-19.md`.** Phase 0 ran on the simulated-headset rig. Phase 1 is done
(1.1-1.6, labs + sim; not headset-tested). Phase 0 showed the frame is CPU-bound after the DLSS fix (the game's main thread), so
Phase 2B/2C and mod CPU on that thread came first; 2A.1 has a design and an observe-only prototype; 3 and 4 are not started.

(bloom, god rays, DOF, lens flares off).

Budget against the measured 14.5 ms (1.05x) and the >= 12.2 ms floor seen at 0.5x:

| Refresh | Budget | Short by at 1.05x (14.5 ms) | Short by at 0.5x (>= 12.2 ms) |
|---|---|---|---|
| 72 Hz | 13.9 ms | 0.6 ms | may fit |
| 80 Hz | 12.5 ms | 2.0 ms | may fit, unmeasured |
| 90 Hz | 11.1 ms | 3.4 ms | at least 1.1 ms |

Conclusion: lowering resolution or AA cannot reach 90 Hz in the heavy areas. The ~12 ms that does not depend on pixels is
engine work per frame and per eye: either CPU (game logic, per-eye pass recording, the NVIDIA driver) or GPU work that ignores
resolution (shadow maps, geometry passes). Phase 0 decides which; Phase 2 attacks it.

## 3. Phase 0: measurement run (gate for Phase 2, about half a day)

Needs the user's go-ahead (AGENTS.md: launching, suspending threads). Sim rig on this PC, the user's last save (the heavy
area of the VD session), `tools/vr_selftest.py --launch --headset-size`, one fixed script so runs compare, stereo mode.

Knobs: `build/native-gpu-timing` (per-pass GPU table `gpu_passes`, `frame_split.gpu_busy`, mod GPU spans). Keep diagnostics on
for the CSVs during measurement only.

| Run | Setup | Answers |
|---|---|---|
| R1 | Baseline: 1.0x, FSR 3 Quality | Per-pass GPU, gpu_busy, frame work |
| R1s | During R1: `python tools/sample_threads.py <pid> 10` | CPU time per thread (game thread, render thread, each job thread) and hottest code: game code, `nvwgf2umx.dll` (driver), or waits |
| R2 | R1 at 0.5x | Confirms E1 in a controlled run; pixel share of each pass |
| R3 | R1 with mod features off (`full-body`, `hand-body`, `dual-wield`, `world-hand-depth`, `note-tablet` knobs removed) | Engine work the mod's features add (extra skinned draws, shadows of the body) |
| R4 | `build/perf-mono-view` | Cost of the second view on this PC |
| R5 | Performance mode | AER saving on this PC |

Decision rule (from R1/R1s):
- `gpu_busy` >= 0.9 and the fixed passes (shadows, depth, culling, probes) dominate -> **2A** first.
- `gpu_busy` < 0.8 and a job thread, the render thread or the driver is near 100 % -> **2B** first.
- The game thread near 100 % -> **2C** first.
- R3 saving > 1 ms -> add the feature costs to Phase 1.

Limits: the sim has no compositor and no VD encode, so finish with one headset run at the same spot (`artifacts/` status +
`xr-frame-timing.csv`).

## 6. Phase 3: performance mode as the safety net (parallel to Phase 2)

Alternate-eye rendering halves the per-eye work, which is exactly the cost E1 points at, CPU or GPU. Dying Light VR ships it on
by default; the reference mod measured 8.7 vs 14.8 ms GPU; our own headset test saved about a third of the frame.

| # | Change | Effort |
|---|---|---|
| 3.1 | R5 measures the saving on this PC. If stereo stays over budget for several seconds, offer (or, as an option, switch to) performance mode automatically, and back when there is headroom. | M |
| 3.2 | Compare our rebuild (`src/stale_eye_warp.hpp`, `src/afw2.hpp`) with Dying Light's AFW (`dlssflat.cpp` in their repo): two-source rebuild (the held eye's last image and the fresh eye's image), the stale-surface test (fresh eye > 1.5 % deeper over 5x3 -> take fresh), the 250 m sky clamp, body/weapon mask redraw at the current pose, 2x motion vectors for each eye's two-frame-old upscaler history. Adopt what we lack. GPL-3.0: ideas only unless licences are compatible. | M-L |

## 8. Not doing

- Frame generation: D3D12-only upscaler APIs, adds latency, not native fps.
- Mono rendering (UEVR PR #442): loses stereo depth.
- Redundant-state elision: measured no gain (v997, v998).
- Broad cvar presets: nothing qualified on 2026-10-21; only the shadow re-test at the heavy spot (2A.2).
- The governor as the heavy-area fix: 0.5x did not help (E1).

## 9. Order and expected outcome

1. Phase 0 (half a day) and Phase 1 (2-4 days) start together; 1.1 needs no game run (GPU lab on the RTX 5070).
2. Phase 2 branch chosen from R1/R1s. The cheapest likely wins: 2A.2 (cvars) and 2B.3/2B.4 (mod time) close the 72 Hz gap
   (~0.6 ms at 1.05x); 90 Hz (3.4 ms) needs 2A.1 + 2A.3, or 2B.1/2B.2, or performance mode.
3. Phase 3 runs alongside as the guaranteed path to 90 Hz on mid-range PCs.
4. Phase 4 last, once the defaults it sets have been measured.

## 10. Rules for every change

- Own build knob (opt-in first, default after headset confirmation) and a lab check, as in `docs/ENGINE-PERF-PLAN.md`.
- Sim A/B on the same save and script, then one headset run at the same spot; simulated checks do not establish headset image
  quality or comfort.
- Verify engine assumptions against live memory before engine changes (AGENTS.md).
- No game launch, injection, input, thread suspension or knob change without the user's go-ahead in the current conversation.

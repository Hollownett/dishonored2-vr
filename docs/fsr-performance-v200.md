## Proven failure: selected FSR scaling never applied

In v200, `apply_upscale()` returned immediately when `full_scale_requested` was true. Normal headset sizing required that same flag. Consequently Quality/Balanced selections could enable FSR but never change its fraction or the native scale caches. The final result confirms `fsr_upscaled=0`, `upscale_active=false`, 30,588 replacements and exactly 15,294 dispatches in each eye, with zero FSR failures/create failures. Every retained timing row reports fraction 1000 and actual per-eye FSR input 2496x2688. Selection 3 (Quality) occurs only in menus/settings in this retained window; selection 4 (Balanced) also has tracked gameplay, still at full resolution.

This explains why lowering the selected quality was not a valid lower-resolution performance experiment. It does not establish the cause of all observed image degradation or judder. The parent owns the scale transaction/restoration fix; revalidate actual native viewport dimensions as well as FSR inputs after that fix.

## Pipeline audit and next instrumentation

1. **Measure native work before optimizing scheduling.** Native eye-begin ownership is already classified in `observe_eye_begin()`; both eyes share scene targets and render sequentially. The left final image is copied before the right overwrites the backbuffer. Add asynchronous GPU timestamps at verified immediate-context boundaries: left begin, right begin, Present before XR work, and after XR transfer/mirror. Associate every query with Present/epoch/AA/fraction/dimensions. This measures native left/right work and bridge GPU work separately. Poll with `DONOTFLUSH` in later Presents, never wait for results. Add matching CPU counters around native view recording and command-list Finish/Execute, including list count/restore flag. These boundaries use already verified hooks rather than a new engine ABI.
2. **Verify actual reduced native work.** Existing FSR dimensions describe the submitted FSR input subrect; they do not alone prove that all G-buffer/HDR/depth rendering used a smaller viewport. Log the native scene viewport/target extent once per eye and mode, from existing viewport/target hooks. Then take matched stationary-scene samples for off/native TAA/FSR Native/Quality/Balanced, same output/mirror/settings, warm up histories and queries, and compare native GPU intervals plus CPU pacing. Retained traces currently lack a matched Quality/Balanced gameplay comparison.
3. **Account for full-resolution stages.** Upscale mode currently bypasses native TAA with a copy, lets the native post-tonemap bilinear upscale draw run, then overwrites it with FSR output and a full output copy. This duplicates native upscale work. Parent can consider suppressing only the positively identified native upscale draw after verifying the target setter, its state changes and an always-valid fallback. Do not remove arbitrary draws or native state setup. The left-eye preserve copy, two XR output copies, optional mirror and post-output processing remain display-sized. Timestamp them before changing resource ownership.
4. **Check steady-state allocations separately.** FSR contexts and scratch resources are recreated only when descriptors/fraction/validity change; queries are retained. Jobs/list nodes allocate on each split, and queue lookup/state preservation have CPU costs not isolated by the current CPU fields. Final global texture-create counts include native resources and do not establish a bridge allocation leak. Add create/recreate and queued-job high-water counters per mode before pooling anything.
5. **Keep readbacks outside benchmarks.** Normal FSR timing uses timestamp/disjoint queries with `DONOTFLUSH`; no blocking poll/Flush was found in that path. Optional depth dump and transfer/UI verification use staging-copy/Map readbacks and can stall. Existing readback markers exclude capture rows from pacing comparisons, but native render timing must also mark any optional depth dump. All three gameplay groups above have zero tagged capture readbacks; that is not proof every possible native Map is absent.
6. **Preserve accepted camera/locomotion.** `GameXr` calls wait/begin from Present and predicts the next native render stage by one runtime period. It is a deliberate one-frame pipeline. Moving xrWaitFrame to another thread or changing prediction requires an independently validated frame-state/pose ownership design; it is not justified by wrapper timing alone. Current API waits contribute mainly to tails. First fix proven scaling, then measure native GPU/CPU spans before restructuring frame submission.

The smallest initial measurement is a GPU elapsed span from the first native immediate Execute after the prior Present to the next Present before XR transfer, plus an end timestamp after XR transfer. That includes submission gaps/queue idle and FSR, so label it **submission elapsed**, never GPU busy time. For narrower coverage, the existing execution lambda wrapping `TaaDispatchHook::execute_original()` receives individual native prefix/remainder lists; per-list timestamp pairs there exclude intervening FSR dispatch without changing any engine ABI. A sum covers only those lists, not every immediate native draw/copy. Report list count and coverage. Use one frame-level disjoint query enclosing timestamp pairs: Microsoft recommends timestamp-disjoint once per frame or less. Avoid nesting a frame disjoint bracket with the current independent per-eye brackets; consolidate them or gate per-eye timing during that diagnostic run.

## Primary references checked 2026-10-10

- [AMD FSR3 upscaler manual](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-upscaler/): render vs presentation resolution, separate TAA is unnecessary when FSR replaces it, pre-upscale image effects can run cheaper, while output-resolution reconstruction remains necessary. The current integration uses FSR3 upscaling; it is not an FSR frame-generation path.
- [Khronos OpenXR frame submission guide](https://github.com/KhronosGroup/OpenXR-Guide/blob/main/chapters/frame_submission.md) and [OpenXR specification](https://registry.khronos.org/OpenXR/specs/1.0-khr/html/xrspec.html): wait/begin/end frame ownership and pipelining; predicted display periods do not measure scanout performance.
- [Microsoft immediate/deferred rendering](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-render): deferred query results become available only after list execution and are read from the immediate context.
- [Microsoft ExecuteCommandList](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-executecommandlist): saved/restored state has a cost; preserve the caller's requested semantics until measured and verified.
- [Microsoft Map](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-map): Map can encounter GPU-busy resources; DO_NOT_WAIT reports still-drawing instead of waiting.
- [Microsoft D3D11_QUERY](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_query): timestamp differences require a reliable disjoint-query frequency; use timestamp-disjoint once per frame or less.

No full-frame GPU timing, compositor dropped/reprojected-frame measurement or headset visual/comfort acceptance was established here. The runtime period and adjacent CPU intervals must not be reported as measured headset FPS.

## Optional native-list diagnostic helper

`src/native_list_gpu_timer.hpp` implements the narrower native-list measurement with a retained ring of eight frames, each with at most 128 timestamp pairs and one disjoint bracket. `prepare(device)` allocates queries ahead of recording. In the existing execution lambda, use `begin_list(context)`, call the original native Execute, then `end_list(context,ticket)`. Ticket zero means rejected/dropped. `finish_frame(context)` closes the bracket before XR transfer; call it for every frame boundary, even when no tracked scene is submitted. Later `poll(context)` uses `DONOTFLUSH` and never blocks. `clear()` belongs to the immediate-context owner and closes any active bracket before releasing references.

`stats()` reports completed frames/lists, latest and accumulated list sums, latest and accumulated first-list-to-frame-end elapsed spans, dropped frames/lists, incomplete poll attempts, disjoint clocks, query failures and rejected calls. Latest coverage includes `last_lists` and `last_dropped_lists`. A 129th list is explicitly dropped while the frame publishes a partial sum; a full frame ring suppresses sampling until that frame boundary so it cannot silently start halfway through the frame. Device/deferred-context mismatch and stale tickets are rejected. Configuration changes require `clear()/prepare()` or recording the configuration by sample sequence; do not attribute asynchronously completed old queries to the current AA mode. FSR eye disjoint timing must be disabled in this diagnostic lane.

Focused `tests/native_list_gpu_timer_check.cpp` compiles under MSVC C++17 `/W4 /WX` and passes on WARP and the real hardware D3D11 device. Checks use real deferred lists, asynchronous publication, multiple lists, capacity/partial coverage, foreign/deferred ownership rejection, stale tickets across cleanup, ring reuse and cleanup with an open bracket. Test-only Flush/poll deadlines provide progress; production code contains no Flush, wait, sleep or readback. These synthetic command-list checks establish timer behavior, not native game throughput.

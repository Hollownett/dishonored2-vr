# Spacewarp / AFW improvements: open techniques we can adopt (2026-11-26)

Research only. Nothing was built or run; no repo file except this one was changed. Our numbers are from the repo docs (2026-11-19 headset
and offline results, 2026-11-25 Linux sims). Web facts are marked **[V]** (read on the cited page by a fetch tool that summarises pages, so
treat quotes as paraphrase) or **[I]** (inferred, or only a search snippet). The reference mod text was read as data, not run.

Naming used below (the docs use three things that the brief folds together):
- **Spacewarp** = `SpacewarpPass`, true-stereo extrapolation at half rate (45 real to 90 shown), the launcher default. Docs: `docs/SPACEWARP-PLAN-2026-11-19.md`.
- **Built-in warp** = `StaleEyeWarp` + `Afw2Pass`, performance mode "alternate eye": one eye rendered per frame, the other rebuilt from its own old image.
- **AFW** = VR Stereo Hub's held-eye rebuild (`third_party/vsh_afw`, zlib, modified), the second renderer in performance mode.
The 2026-11-25 A/B (AFW vs built-in) compares the last two. Spacewarp is a different pass with its own weaknesses (section a).

## (a) What we have, in 15 lines

1. Spacewarp (`src/spacewarp_pass.hpp`, GPU port of `tools/spacewarp_replay.cpp`): at pacer k=2 the engine renders every second slot; after the real
   frame's `xrEndFrame`, `generate_spacewarp_` (`src/game_xr.hpp:3119`) draws the next slot's eye from the kept final image + full-res depth + motion
   texture + rig mask, runs `sw_pass_->run` (`:3412`), and `submit_spacewarp_` (`:3604`) submits it at the next Present (or a safe mid-frame point, `src/spacewarp_safe_mid.hpp`).
2. Per source texel a 3D point from reverse-Z depth, moved by class (`spacewarp_pass.hpp:1-17`, `Classify :404`): hands by their controller's tracked rigid change,
   rest of rig by the play space step, torso/legs by solver steps, world movers by the motion texture x `motion_share` (capped by `mover_cap` = 3 cm, `:89`), still world by pure parallax, sky by rotation.
3. Splat: `Land :467` -> `SplatDepth :480` (InterlockedMax on 1/z, ONE source texel to ONE render-size cell), `SplatIndex :483`.
4. `Crack :490` (radius 2, closes seams on magnified surfaces), `Fill :516` (farthest of the first surfaces in 8 directions), `Uncovered :575`/`Blend :590` (8-direction 1/d blend), `BlurBlend :599` (7-tap tent), `Resolve :611` (back-project each output pixel into the source colour, bilinear in linear light).
5. Cameras: `src/spacewarp_math.hpp` (D = dO^a * O * dV * V; head from the runtime's located pose, locomotion from the last three real frames); `src/warp_play_space.hpp` holds the per-render play space used by the alternate-eye path.
6. Built-in warp (`src/afw2.hpp`, Metro AER+ style, ~1.14 ms on the laptop at sim size, ~2.0 ms on RTX 5070 at 2246x2419): per-texel own motion (`Scatter :391`, `Motion :557`, `Repair :600`), forward `Splat :743`, `Crack :767`, 10-pass jump-flood `Fill :828`, per-texel `Decide :1150`, Catmull-Rom resolve; fresh-eye colour only for hands/holes. Layers and dispatch in `src/stale_eye_warp.hpp:281`.
7. AFW (`third_party/vsh_afw/core/gfx/afw_warp.cpp`, adapter `src/afw_vsh.hpp`): per held-eye pixel hands/weapon from the fresh eye (depth reprojection), world from the held eye's own last image carried by the camera change, fresh world where the stale test fails, plus a disocclusion fill. 0.55-0.63 ms. Called first at the held-eye seam (`game_xr.hpp:3042`), built-in warp on refusal.
8. Spacewarp and performance mode are mutually exclusive (`docs/AFW-RENDERER.md`); Spacewarp wins.
9. Measured, same-frame A/B (`docs/AFW-RENDERER.md`, 5 runs x 140 sets, 640x640, luma error in moved regions, lower is better):

| Motion | AFW | built-in | none |
|---|---|---|---|
| head sway | 14.5 | 15.1 | 21.3 |
| arms sweeping, slow / fast | 22.0 / 24.7 | 25.3 / 27.8 | 32.0 / 34.5 |
| head flick | 8.8 | 8.7 | 11.2 |
| walking | 14.4 | 15.0 | 15.4 |

10. Weakness W1, **hands while walking**: both warps put the hands where the game does not draw them during the walk bob; around the hands that is worse than the held frame (AFW-RENDERER "Measured"). Walking overall is only 4-7 % better than no warp.
11. W2, **speckles**: built-in breaks a moving sleeve into see-through dots, ~5x (3-4x per the brief) more than AFW. W3: AFW leaves blocky light wedges at a moving arm's trailing edge and is ~10 % softer; built-in adds 5-10 % speckle.
12. W4, **head flicks**: tie, no gain from either beyond a rotation reprojection (8.7 vs 11.2). A fast flick uncovers the image edge.
13. Spacewarp-specific known limits (plan s.4, s.18-s.30): faint star pattern in uncovered areas, cracks on very close magnified surfaces, fast movers lag (3 cm cap), transparents/particles carry the depth of what is behind them, snap-turn cuts, `sword_sweep` (attack animation drives the hand, not the tracked pose) = no method beats the held frame (7.1 vs 6.9).
14. Spacewarp offline result that matters for ranking: own sw beats rotation-only reprojection (what a runtime without app depth can do) on walking 6.68 vs 18.63 and running 5.09 vs 14.84 (plan s.9); exact hand poses equal the hand oracle there. So the camera/hand maths is solved; remaining error is in fill, splat coverage, movers, and unobservable content.
15. Not yet done: `XR_KHR_composition_layer_depth` submission (offered by VDXR and SteamVR per our v1105 probe; `docs/PERF-PLAN-90HZ-2026-11-19.md:135` item 4.4 "verify benefit"; grep finds no use in `src/`). `XR_FB_space_warp` not used (`SPACEWARP-PLAN:144`).

## (b) What the reference VR mod does (MIT; READ ONLY)

Repo a local checkout of the reference mod, D3D12 only. Three separate things:

**1. FSR3 per-eye generator** (`src/Framegen/Fsr3.cpp`, `include/Framegen/Fsr3.hpp`, commit `dc0b2c58` 2026-11-21 "Add iPowerTech per-eye ... FSR3 interpolation and extrapolation"). Adapted from the iPowerTech fork. Settings `kInterpolation` (default) / `kExtrapolation`; FidelityFX SDK `ffx_frameinterpolation` + `ffx_opticalflow` through the DX12 backend, optical flow optional ("for what the engine's vectors miss"). Default generator per README / commit `6f33af62`: NVIDIA OFA at half res + FidelityFX interpolation, not DLSS-G. Interpolation shows a midpoint between two captures, i.e. it holds a frame back (latency). Cost: "1.3-1.5 ms for both eyes at 2560x2560" without optical flow (commit message of the 0.2.x consolidation).

**2. Extrapolation mode (their latency-free option)**, `src/Framegen/Fsr3Extrapolate.cpp`, `Fsr3.cpp:414-489`, `Presenter.cpp:160-211`. It is deliberately minimal:
- Per eye, one compute gather: output pixel q takes colour at s where `s = q + Factor * mv(s)`, three fixed-point iterations, point-sampled vectors (`Fsr3Extrapolate.cpp:20-39`). Colour is the capture (display size), motion is the render-size vector field after **dilation**.
- Dilation (`Fsr3Dilate.cpp`) is a port of AMD's `FindNearestDepth` 9-tap (motion vector borrowed from the nearest-depth tap, not the centre) + bilinear scatter of previous depth with `InterlockedMax/Min` on bit-cast depth. They found a plain store caused motion-proportional ghosting (comment block at the top of the file): use interlocked scatter.
- `kExtrapolationFactor = 0.5` fixed, "a fixed half for the first test" (`Fsr3.cpp:414-417`); the headset shows the extrapolated frame half a game frame after the real one; the pose label for that frame is `Ahead(previous.pose, current.pose, .5)` = linear extrapolation of the two last poses (`Presenter.cpp:204`).
- Extrapolation only runs when the next display cycle would otherwise repeat the capture (`result.kind == Repeat`, `:161`), so real frames go out immediately.
- **Disocclusion: none of its own.** "Where a moving object uncovers what was behind it, the nearest moving pixels stretch over the gap -- the first test is whether direction and amount are right, filling what is uncovered comes after" (`Fsr3Extrapolate.hpp`). No depth test, no far-biased fill, no hand/body class. Their depth is only used for the dilation.
- Cuts: `in->camera.reset` -> no extrapolation (`Fsr3.cpp:430`); `CameraJumped` check; **snap turns** are not flagged by the engine, so `NoteSnapTurn` marks one of the next 6 captures whose camera turned more than half the snap angle as a cut (`Fsr3.cpp:238-250`). Head turns alone never count. (We handle cuts by step thresholds, `cut_step`; their snap-turn hint is a cheap addition for ours.)
- No numbers are published for extrapolation quality; only a status line ("Extrapolating: engine motion vectors, half a game frame ahead").

**3. "AFW" / "OSR"** (the other-eye rebuild, one eye per frame): PureDark's closed `PDAFWPlugin.dll` (`docs/afw-20261103.md`, 1.59 ms/frame GPU, CPU-bound street 68.7 fps vs engine stereo 66.2) and the port's own **OSR** (`docs/osr-20261104.md`, `src/Render/Osr.cpp`), written from the *description* of OFXR-Bridge's GPL OSR (they did not copy). OSR = four compute passes: (1) copy drawn-eye colour+depth to history, (2) splat each depth texel through its camera into the made eye's depth grid with **2x2 footprint, InterlockedMax**, and splat the made eye's previous frame into a second grid, (3) resolve: trace the cell depth back into the drawn eye, take colour if depth agrees within 3 %, else the previous frame, else hole, (4) fill a hole by **mirroring the farther bounding pixel across the edge**, searching 384 px in strides, then column, then farthest bound. Hand rules: previous-frame surfaces are dropped where the drawn eye sees past them (`StillThere`); anything <1 m not confirmed is the player's body and dropped; a drawn sample next to a nearer surface (within 1.5 depth texels, parallax differing >0.75 px) is left to history/fill to stop a thin copy of the near outline. Depth jitter: subtract the frame's jitter (best of three tested: 35.7/37.9 dB worst/mean vs 33.3/36.3 PureDark AFW; ~31 dB with no jitter correction). GPU: OSR 0.44-0.61 ms vs AFW 1.59 ms. Stated limits: object motion not extrapolated, mirror fill "does not invent detail".

**HUD / hands.** HUD panels are drawn per eye **after** the warp, "HUD does not shake with the eyes taking turns" (`afw-20261103.md`); `xr_hand_lerp_framegen_scale` 1.5 raises hand smoothing under framegen (commit list); under AFW launches normal framegen is off. Engine-drawn flat elements are warped with the scene (open item). **Depth/MV**: reverse-Z engine depth, motion scale = fraction of image x eye size; motion types `FromOtherEye` / `Normal` (a `Normal` type or no MV doubles the moving arm in a sweep; `CombinedWarping`+`FromOtherEye` is clean on arms).

**Tried and rejected** (`docs/steamvr-hitches-20261113.md:101`): extrapolating *late* frames along the motion vectors up to a whole game frame. Numbers improved (world freezes 0.36-0.46/s vs 0.92-1.28; resends 0.1 vs 0.9) but "it looked bad in the headset, 3-4 such images a second, and was reverted". Relevant to us: a generated frame covering a whole period (not a half) is visibly worse; their measured stutter count is not a quality metric. Their AER v2 (NVIDIA Optical Flow synthesis, 48 vendored files, ~9900 lines) was removed in full.

**Take-aways for us.** Their extrapolation is far simpler than ours (no depth test, no fill, no classes); what we can use is (i) AMD's nearest-depth motion dilation with interlocked scatter, (ii) OSR's splat footprint, mirror/background fill and `StillThere` ideas (technique only), (iii) the snap-turn cut hint, (iv) HUD after warp (we already do). They have no published error metric, so there is nothing to benchmark against.

## (d) Ranked recommendations

Each is its own build knob, off by default until the sim A/B passes, then a headset check. The sim rig: `tools/linux/scenarios/afw_ab.py` / `afw_ab_pistol.py` (same-frame A/B, scored by `afw_ab_score.py`), `spacewarp capture N` + `tools/spacewarp_capture_ab.py` for Spacewarp, `tools/stale_warp_defects.py` regions. Metrics: luma error vs the real next frame per region (moved, hand, world, edge ring), speckle count (isolated pixels whose luma differs >24 from all 8 neighbours inside the moved mask), ghost share. Ship a change only if it is no worse than the current build on every region and better on its target.

### R1. Hand-region safety net while walking (fixes W1; own code, ~0 ms)
Evidence: in the walking A/B both warps are *worse than showing the old frame* around the hands (AFW-RENDERER), and Spacewarp's sword sweep is the same story. The 2026-11-19 offline result says hands with exact controller poses equal the oracle, so the failure is where the game's drawn hand does not follow the tracked pose (walk bob, attack animation) [diagnosis not yet done; this is the first thing to measure].
- Step 1 (diagnostic, no code in shaders): in the capture scorer add a region `hand` (rig mask in the held-eye paths; palm sphere + weapon line in Spacewarp) and report error for {held, warp-as-is, warp with hand moved by the drawn grip change}. The drawn grip change is already available (`kept_camera` / `WarpPlaySpace::hands`, `warp_play_space.hpp`; Spacewarp `drawn grips` in `game_xr.hpp` `generate_spacewarp_`).
- Step 2: gate. Per hand, if the |drawn-grip delta (head-relative, over the extrapolation interval)| is below ~3 mm / 1 deg the hand pixels keep the old frame (AFW's `stillmm`/`stilldeg` already do this for AFW: raise default or extend it to "walking bob" = head-relative hand delta dominated by vertical oscillation); if the drawn grip and the controller grip disagree by more than a threshold (the hand clamp's hold, plan s.17), use the *drawn* grip only. In the built-in warp, `Decide :1150` takes the gate as a per-class flag; in Spacewarp `SpacewarpParams::hand_on` (`spacewarp_pass.hpp:55`) per hand.
- Proof: `afw_ab.py` walking phase and `run_hands`-style Spacewarp capture; target: hand-region error <= held frame in walking, no regression in "arms sweeping" (22.0 / 24.7 AFW, 25.3 / 27.8 built-in). Risk low; if the hand region simply cannot be predicted, the safe floor is the held frame.

### R2. Speckle-free moving surfaces: dilated mover vectors + 2x2 splat footprint (built-in warp and Spacewarp; ~+0.1-0.2 ms)
Target W2 (5x dots on moving sleeves) and the Spacewarp "cracks on close surfaces" (FRAMEGEN-OTHER-MODS items 2 and 4).
- Add a 3x3 nearest-depth dilation pass for the mover motion texture before `Classify` (`spacewarp_pass.hpp:404`) and `Motion` (`afw2.hpp:557`): take the vector from the tap with the nearest depth (technique and caution on scatter writes from `Fsr3Dilate.cpp`: use `InterlockedMax` on bit-cast depth, a plain store ghosts proportionally to motion, found live by the CP port).
- In `Land`/`SplatDepth` (`spacewarp_pass.hpp:467-483`) and `Splat` (`afw2.hpp:743`): when the splat's local expansion (landing of the texel vs its +x/+y neighbours) exceeds 1, splat a 2x2 footprint, guarded by same-surface depth (within 5 %) so silhouettes are not fattened (OSR does an unconditional 2x2; we should not).
- Proof: sim `afw_ab_pistol.py` and the arms-sweeping phases: speckle count must fall from ~5x AFW to ~<=1.5x; moved-region error must not rise; `Edge` region (silhouette ring) not worse. Knob: `no-spacewarp-dilate-movers` style inverse so A/B is same-frame (the capture already supports `spacewarp altmovers`).

### R3. Pyramid inpainting for uncovered area colour, replacing 8-direction blend + tent (Spacewarp; ~0.1-0.3 ms, maybe net-zero)
Target the star pattern and anisotropic seams. Keep `Fill` for seed/depth/class bookkeeping (`spacewarp_pass.hpp:516`), replace `Uncovered/Blend/BlurBlend` (`:575-610`): build a mip pyramid over drawn (not filled) cells with weights coverage x far-surface bias x same class (keep the class and 3/4-depth gates the plan already has), push down, fill holes only. FSR3 uses exactly this idea [V per FRAMEGEN doc; I did not read the shader source]. Port by hand to SM5. Evidence is circumstantial: AFW's lower speckle comes from its fill/gate design (unread). Proof: `spacewarp_pass_check` lab test 14 (striped wall) for the star; capture A/B on `spacewarp capture` triples with region `uncovered` (pixels `Uncovered()` true); head-flick phase must not worsen at the image edge. If R2 already removes most speckle, drop R3.

### R4. Submit depth to the runtime (`XR_KHR_composition_layer_depth`) and measure whether the runtime uses it (head flicks, late frames; ~0 ms)
Head-flick error is a tie (8.7 vs 8.8) and both are only 2.5 levels better than no warp: that content is rotation, which the runtime already corrects, plus an image-edge disocclusion neither can invent. The one thing a runtime *can* do better with app depth is residual head translation on generated and late frames (ASW 2.0 PTW: [V] depth must match colour size, D32 preferred; cost "lost in frame timing noise"). This is the one low-effort item that takes the runtime's compositor work, which is free GPU time, but whether VDXR and SteamVR use it is **unverified** (no primary source found; SteamVR reportedly forwards it only to the Oculus runtime [V via Godot PR in search]). Plan: add the layer chain to the eye projection layers only (the depth copy exists: FsrTaa's depth copy, `game_xr.hpp:315`), linear depth in metres or reverse-Z with correct `nearZ/farZ`; keep a knob; test on VDXR and SteamVR in the headset (sim cannot show it: the simulated runtime ignores locate times and does no reprojection). Verify there is no double correction against our own head-extrapolation (Meta's rule: ASW and PTW must correct different motion [V]). Do not count this as proven until a headset A/B on a deliberate 60 Hz hitch.

### R5. AFW: a post-pass sharpen, then re-run the A/B (softness; 0.05-0.1 ms)
AFW is 10 % softer than the real frame. Our built-in warp has Catmull-Rom + detail restore (`afw2.hpp` resolve) because bilinear lost 11-16 % detail (v803). Try (a) our `EyeSharpen` pass after the AFW rebuild on the held eye only (it already exists), (b) the depth-jitter subtraction from OSR (item 17) if our depth copy carries jitter. Proof: `afw_ab.py` "head sway" and "walking" phases, error plus a high-frequency energy ratio (rebuilt vs real next frame, 8-level high-pass); target softness <= 3 %, no halo (edge-ring error not worse). Low risk, cheap, and measurable in an hour.

Not ranked but cheap and worth doing alongside: snap-turn cut hint (item 16, CP), mover-cap confidence gating (item 6, plan FRAMEGEN item 3; do after R2 because the same motion texture feeds it).

## (e) What NOT to do and why

- **Do not adopt FSR3/FSR4 frame generation, DLSS-G, XeSS-FG, or Lossless Scaling.** They interpolate: they need the next real frame and add a frame of latency to hands and head, exactly what extrapolation avoids (plan s.8). The CP port's own default (interpolation) has that cost, and they keep an extrapolation mode for the same reason. FidelityFX SDK targets DX12/Vulkan [V]; our session is D3D11 and the game runs under DXVK. Take shader ideas (dilation, inpainting), not the pipeline.
- **Do not make FSR3 optical flow our primary motion source.** SteamVR Motion Smoothing and VD SSW use flow and ship "repeating pattern" artifacts [V]; we have exact poses and engine vectors. A 3-way fusion costs more than the whole warp budget. Only reconsider if a debug view (FRAMEGEN item 5) shows many objects with no vector.
- **Do not copy GPL code.** Dying Light VR (GPL-3.0) and OFXR-Bridge's OSR (GPL-3.0 per the CP docs) are technique references only; the repo already forbids copying (`docs/PERFORMANCE-MODE-AFW-COMPARISON.md`). The CP port's code is MIT and the FidelityFX SDK's shaders are MIT-style [V: "MIT-style licence covers the SDK source and shaders"; one section of the SDK licence is a custom AMD binary-only licence, so check each file], OpenWarp is NCSA (attribution), AFW (vsh) is zlib. Keep credits in `THIRD_PARTY_NOTICES.md`.
- **Do not chase neural extrapolation (ExtraNet, ExtraSS, GFFE, PatchEX).** No public code or weights were found [V search], they need a per-game trained network and G-buffers or an ML runtime, and published costs are far above 1 ms on a laptop GPU [I]. PatchEX is claimed 2x faster than ExtraSS [V abstract], still not near our budget.
- **Do not extrapolate a whole period.** The CP port tried a full-game-frame extrapolation for late frames and reverted it because it "looked bad in the headset" even though counters improved; our own plan limits to one slot (half a period at k=2). Generated frames under high-motion should fall back to repeat, not stretch.
- **Do not lift the mover cap blindly** (already tried, plan s.19) and do not give transparents/particles the mover's full vector (Meta lists one-MV-per-pixel as AppSW's weakness [V]).
- **Do not rely on `XR_FB_space_warp` for PC.** Documented as an OpenXR extension for Quest (Vulkan) apps; no source shows VDXR, Quest Link or SteamVR implement it [unverified]. Its MV/depth are low-res by design and Meta's own sample ties that to thin-geometry artifacts [V]. At most add an extension probe to the existing runtime log (read-only, zero risk) so the next headset session records whether it is offered.
- **Do not stack warps** (Spacewarp + AFW/built-in + runtime SSW/Motion Smoothing): double generation; keep VD SSW off (`docs/PLAYING.md`).
- **Do not trust sim scores for hands and head.** The simulated runtime returns the current pose for any requested time (plan s.10, s.30), so head extrapolation, the torso step and hand extrapolation are never exercised; R1 and R4 need a headset check. Offline replay scores also use the exact destination camera.
- **Do not read GPL sources to "check" our design**; if a behaviour needs confirmation, test it in the sim.

## Open questions / unverified

- Whether VDXR, SteamVR (OpenXR) or Quest Link use submitted depth for positional reprojection: no primary source found (R4).
- Whether any runtime on PC exposes `XR_FB_space_warp`: no confirmation either way; the Khronos page only gives the registry entry.
- The FSR3 interpolation technique page text I could read did not include the inpainting pyramid details (page truncated at 100k chars); our existing note (`docs/research/FRAMEGEN-OTHER-MODS.md`) says VERIFIED but through a summarising fetch. Re-read the shader `ffx_frameinterpolation_*` sources in the SDK before R3.
- AFW's internal fill (`third_party/vsh_afw/core/gfx/afw_warp.cpp`) was not read for this report; it is the in-repo reference for why AFW has fewer speckles and should be read before R2/R3 (it is zlib, so porting is permitted).
- Costs in column "GPU cost" are estimates, not measured; measure with `native-gpu-timing` spans (`afw_rebuild`, `afw_capture`, Spacewarp pass).
